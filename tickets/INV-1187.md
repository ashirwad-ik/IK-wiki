## Architecture — how tiers are decided

- **Regular Hint click** → worker passes full live context (module, question, code buffer, transcript tail, prior hints on the question, which button was pressed) to the LLM; LLM returns strict JSON `{tier, text}`.
- **Still stuck → Approach / Walkthrough** → FE sends `{force_tier: "APPROACH" | "WALKTHROUGH"}` in the RPC payload; worker honors it verbatim, LLM's tier field is ignored.
- **Behavioural + Walkthrough** → BE 422s at the record endpoint. Worker also silently downgrades to APPROACH before persisting, defence in depth. FE hides the Walkthrough button on Behavioural so the force path can't hit it.
- **Fallback** → if the LLM returns malformed JSON, worker falls back to a deterministic count-based ladder so the UX degrades gracefully.
- **Soft cap** — 50 hints per question, warn-and-serve, never user-facing. The cap exists purely to catch runaway loops.

## Contract (locked across the three repos)

- **LiveKit RPC**: method `request_hint`. Payload is `{}` (agent picks) or `{force_tier: "NUDGE" | "APPROACH" | "WALKTHROUGH"}` (user forces). Response is JSON string `{tier, text, hint_id, question_index, module}`.
- **BE record endpoint**: `POST /api/v1/ai_mock_interview/interview/{id}/hint`, guarded by `X-Internal-Api-Key`, idempotent on `(interview_id, hint_id)`, 422 on Behavioural + WALKTHROUGH.
- **BE summary endpoint**: `GET /api/v1/ai_mock_interview/interview/{id}/hints/summary` → `{hints_used, by_tier, by_question, penalties}`.
- **Main report payload** also carries `hints_used` and `hints_breakdown`; legacy interviews return `0` / `[]`.
- **Table**: `ai_mock_interview_hints (id, interview_id, sub, question_index, tier ENUM, hint_id VARCHAR(64) UNIQUE on (interview_id, hint_id), text TEXT, served_at, created_at)`.

## Lessons learned (worth preserving)

- **Branch off `qa`, not `main`.** BE devs merge feature branches straight to `qa`; `main` only gets infra/CI batched in periodically. Branching from `main` picks up every other dev's pending main-only work and makes the PR diff enormous. The diff from `qa` is the one that matters.
- **BE/Worker do not auto-deploy on push to `qa`.** Each has a `deploy-qa` workflow with a hard guard `if: github.ref == refs/heads/qa` and trigger `workflow_dispatch`. You must merge into `qa` and then manually click Run workflow. FE is the only repo that auto-deploys on `qa` push (Vercel).
- **Alembic migrations are NOT run by the BE deploy workflow.** DevOps runs `python scripts/migration_helper.py migrate` against QA MySQL after deploy lands. Without that step, the hint endpoint 500s on INSERT.
- **`commit-lint` is a branch-name check, not a commit-message check.** Rule: branch must start with `(INV|PDC|PF|…)-[0-9]+`. A `feat/` prefix fails. Rename or branch fresh.
- **Classifier blocks pushes to shared branches (qa / main / production).** Even a plain revert push gets blocked. In practice this is good — it keeps a human in the loop on shared-branch writes. The FE's `qa` auto-deploy is the exception and requires the user to run the push themselves or allow it per-repo.
- **Deploy order is BE → Worker → FE.** BE first so the hint endpoint and migration exist. Worker next because it POSTs to BE. FE last so users never see a Hint button that hits a 404 or a worker without the RPC registered.
